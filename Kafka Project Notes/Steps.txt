You created the appointments topic across all three Kafka containers. You haven’t sent any appointment messages yet.
Here is what happened:
1. docker compose exec kafka-1 ran the command inside the kafka-1 container.
2. --bootstrap-server kafka-1:29092 used kafka-1 as the first connection to the cluster. It does not mean the topic exists only on kafka-1.
3. Kafka created three partitions—three places where appointment messages can be stored.
4. Each partition gets a copy on every broker, because you requested three replicas.
An example of how Kafka could assign the leaders:
                kafka-1       kafka-2       kafka-3
Partition 0     LEADER        copy          copy
Partition 1     copy          LEADER        copy
Partition 2     copy          copy          LEADER
Now imagine you send “Appointment 5 created”, and it goes to partition 1:
- kafka-2 receives it because it leads partition 1 in this example.
- kafka-1 saves a copy.
- kafka-3 saves a copy.
The message belongs to one partition, with copies on all three containers.
min.insync.replicas=2 means that, when publishing with acks=all, Kafka requires at least two caught-up replicas available to accept writes.

A broker is a running Kafka server. Its job is to receive, store, and deliver messages.
In your project, each Kafka Docker container runs one broker:
- Container kafka-1 = broker 1.
- Container kafka-2 = broker 2.
- Container kafka-3 = broker 3.
So when I say “the message is copied to three brokers,” I mean:
kafka-1 container → stores the message
kafka-2 container → stores a copy of the same message
kafka-3 container → stores a copy of the same message
If the kafka-1 container stops, the message is still stored in kafka-2 and kafka-3.
For your setup, think “Kafka container” whenever you hear “broker.”


For your appointments topic, each broker stores all 3 partitions:
kafka-1: partition 0, partition 1, partition 2
kafka-2: partition 0, partition 1, partition 2
kafka-3: partition 0, partition 1, partition 2
There are 3 distinct partitions, each stored in 3 copies—so 9 partition copies across the cluster.
Partition 0 on kafka-1 and partition 0 on kafka-2 are copies of the same partition, not two different partitions.

Correct—reading a Kafka message does not remove it.
Think of a partition as a book:
- The message is a line in the book.
- The consumer’s offset is its bookmark.
- Reading moves the bookmark; it doesn’t erase the line.
Other consumers can read the same message, and you can read it again.
Kafka removes old messages according to the topic’s retention settings, such as how long to keep them—not because someone read them.

so in consumer logic should be - not to read the same message twice or more time?



Normally, the consumer remembers where it stopped, using a saved offset—a bookmark.
For example:
1. Read message at offset 0.
2. Process it successfully.
3. Save the bookmark: “Next, read offset 1.”
When it restarts, it continues from that bookmark.
But a message can still arrive again:
1. The consumer processes the message.
2. It crashes before saving the bookmark.
3. After restarting, it reads that message again.
So our consumer should safely handle duplicates. We’ll use each event’s unique event_id to recognize an already-processed event and avoid performing its action twice.
The rule is: process successfully, then save the offset—and make repeated processing safe.

Next is a Python consumer. We’ll start small: it will read an event, print its ID and type, then save its reading position in Kafka.
Unlike your console command with --from-beginning, this consumer will use a fixed consumer group so it can resume from its saved position after restarting.

/////////////////////////////////////////// Python Consumer part /////////

In your project, the appointments topic has three partitions. Suppose we run three Python consumers, all using:
kafka_consumer_group = "appointment-indexers"
Kafka could assign the work like this:
- Consumer A reads partition 0.
- Consumer B reads partition 1.
- Consumer C reads partition 2.
Each partition is assigned to one consumer within that group at a time. With only one consumer running, it reads all three partitions.

The group also has saved reading positions, called committed offsets. For example, after processing an event at offset 4 in partition 0, the consumer saves offset 5 as the next position. When it restarts using the same group name, it can resume there.


Note:
More precisely, the saved pointer belongs to the consumer group:
- Kafka’s end position: 5 → events have been written at offsets 0–4.
- Group’s saved pointer: 3 → next read starts at offset 3; events 3 and 4 remain.
When our consumer restarts with the same group name, it resumes from that saved pointer.

Yes, that’s correct—with one detail about starting:
- Partition’s end position → the next offset for a new event.
- Consumer’s reading position → the next event to read.
A new consumer group starts at the earliest available event if configured with auto.offset.reset="earliest". With "latest", it starts at the end and waits for new events.

So in conclusion when we add event to the partition offset moves forward and points on the next free place to put next event
Consumer has his own pointer ,and when reads event it updates next position to read.
The option to put consumer pointer to earliest (start from the start of partition) 
or from the latest (so it start from the end and wait for event)

- json converts the event’s JSON into a Python dictionary.
- Consumer is the Kafka client that reads events.

Now add this below the imports in app/api/consumer.py:
def main():
    settings = get_settings()

    consumer = Consumer({
        "bootstrap.servers": settings.kafka_bootstrap_servers,
        "group.id": settings.kafka_consumer_group,
        "auto.offset.reset": "earliest",
        "enable.auto.commit": False,
        "broker.address.family": "v4",
    })
This creates our Kafka consumer:
- bootstrap.servers: addresses of your Kafka brokers.
- group.id: the group that owns our saved reading positions.
- auto.offset.reset: starts at the earliest available event when there’s no valid saved position.
- enable.auto.commit=False: we’ll explicitly save the position after processing each event.
- broker.address.family: uses IPv4, matching your local Docker setup.





Next, tell the consumer which topic to read.
Add this inside main(), immediately after consumer = Consumer({...}), using the same indentation:
    consumer.subscribe([settings.kafka_topic])
This subscribes our consumer to the appointments topic. The brackets form a list because a consumer can subscribe to multiple topics.



Next, add the reading loop inside main(), directly below consumer.subscribe(...):

Yes. The loop repeatedly calls poll():
1. If an unread event is available, it returns that event.
2. Otherwise, it waits up to one second.
3. If nothing arrives, it returns None, and the loop calls poll() again.
So the consumer keeps running, reading existing unread events and waiting for new ones.
